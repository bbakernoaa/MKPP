# Feature Specification: E2E Solver Validation & Baseline Testing

**Feature Branch**: `feature/014-e2e-solver-validation`

**Created**: 2026-08-01

**Status**: Draft

**Input**: User description: "we need to do an end to end testing versus something like KPP with known mechanisms for gas kinetics first to test 1) the AOT generation and 2) accuracy of the solvers"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - AOT Generation Verification (Priority: P1)

As a computational scientist, I want to ingest a known, standard gas-kinetics mechanism (e.g., Chapman Cycle or CB05) using the MKPP AOT compiler, so that I can verify the SymPy-generated Unified Jacobians, Adjoints, and C++ headers exactly match or analytically exceed the correctness of the legacy KPP output.

**Why this priority**: Validating the AOT compiler against a trusted baseline ensures that the foundational mathematics (derivatives, Jacobian sparsity) are sound before moving to production deployments.

**Independent Test**: Execute the MKPP Python parser on a legacy `.eqn` mechanism and diff the non-zero sparsity pattern and analytical derivative equations against the output generated by traditional KPP.

**Acceptance Scenarios**:
1. **Given** a standard legacy `.eqn` gas kinetics mechanism, **When** processed by MKPP, **Then** it produces valid, compilable C++ Kokkos headers without manual intervention.
2. **Given** the generated Jacobian, **When** evaluated at a specific concentration state, **Then** the sparsity pattern and numerical values match legacy KPP output to within machine precision.

---

### User Story 2 - Solver Integration Accuracy (Priority: P1)

As a numerical modeler, I want to run the Exaero host utility using the MKPP-generated headers for a defined time-step, so that I can compare the integrated chemical concentrations against a standalone KPP Fortran baseline.

**Why this priority**: Correct Jacobians are necessary but insufficient; the full integration scheme (e.g., Rosenbrock) must be verified to ensure the multi-rate GPU execution preserves strict accuracy.

**Independent Test**: Run a 24-hour simulation box-model using both Exaero (GPU/Kokkos) and the legacy KPP baseline (Fortran/CPU), and calculate the Root Mean Square Error (RMSE) between the two concentration outputs.

**Acceptance Scenarios**:
1. **Given** identical initial atmospheric concentrations and meteorology, **When** both solvers integrate over a test duration, **Then** the final predicted species concentrations match with a relative error of less than $1 \times 10^{-6}$.
2. **Given** the Exaero execution, **When** evaluating the solver over the grid, **Then** the memory layout constraints (CON-002) and GPU team parallelism (CON-001) must remain perfectly intact (zero overhead allocations).

### Edge Cases
- How does the validation suite handle species whose concentrations drop to mathematically near-zero limits (subnormal numbers) during integration? (Should clamp or use absolute tolerance limits).
- What happens if the legacy KPP baseline fails to converge on a highly stiff edge case that MKPP handles easily?
- How are photolysis rates (from Cloud-J) mocked or normalized across the two baselines to ensure a 1:1 gas kinetics comparison?

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST provide a validation fixture (e.g., Python or C++ test suite) that compiles a specific, well-known kinetic mechanism (like the Chapman cycle) using both MKPP and standard KPP.
- **FR-002**: System MUST capture the AOT generated analytical Jacobians and assert structural equivalence (Sparsity Pattern) between the two generators.
- **FR-003**: System MUST execute a time-stepped box-model integration using Exaero's C++ solver.
- **FR-004**: System MUST calculate the relative and absolute error between Exaero's final state array and the legacy KPP baseline state array.
- **FR-005**: System MUST enforce that the Exaero test execution still respects `Kokkos::TeamPolicy` constraints (no warp divergence, CON-001) and `Kokkos::MemoryUnmanaged` LayoutLeft bindings (CON-002).

### Key Entities

- **Legacy KPP Baseline**: The trusted Fortran code generation and solver output used as the ground-truth reference.
- **MKPP AOT Headers**: The newly generated Kokkos C++ headers containing the Unified Jacobian.
- **Exaero Box-Model Runner**: A lightweight C++ test harness wrapping the Exaero utility to execute the chemistry in isolation over a fixed time domain.
- **Validation Fixture**: The script or testing layer computing the RMSE and structural diffs between the two systems.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% successful compilation of the MKPP generated headers for the test mechanism with zero manual modifications.
- **SC-002**: Analytical Jacobian sparsity patterns and matrix values match legacy KPP to within machine precision ($\approx 10^{-15}$ for double precision).
- **SC-003**: End-of-integration gas concentrations across all prognostic species demonstrate a relative error of $< 10^{-6}$ compared to the legacy KPP reference data.
- **SC-004**: Memory profiling confirms 0-byte dynamic allocation during the GPU solver execution step.

## Assumptions
- A legacy KPP executable or pre-generated reference output dataset is available in the testing environment to serve as the baseline.
- The selected gas kinetics mechanism (e.g., Chapman cycle) is purely gaseous (no heterogeneous aerosol physics needed yet) to isolate the core solver accuracy.
- Both solvers use the same integration method (e.g., Rosenbrock) and identical tolerance configurations (ATOL, RTOL).
