# Feature Specification: Exaero C++ Utility & Mechanism Registry

**Feature Branch**: `feature/008-exaero-cpp-utility` (expected)

**Created**: 2026-08-01

**Status**: Draft

**Input**: User description: "Create the specification for the `exaero` native C++ utility (User Story: Kokkos Execution and Multi-Rate dispatch) that will ingest the MKPP headers. Integrate preexisting mechanisms as optional mechanisms in the utility. This way we can have a set of pregenerated mechanisms and then add to it dynamically when we have a new configuration that we may want."

## Clarifications
### Session 2026-08-01
- Q: How should pre-generated mechanisms be linked into the C++ utility? → A: Static Compilation: Mechanisms are conditionally compiled into the main library using CMake flags.
- Q: Who manages the Kokkos execution environment lifecycle? → A: Host Model: The external host application (e.g., UFS/CMAQ) manages the Kokkos lifecycle.
- Q: How should temporary sorting index buffers be allocated? → A: Persistent Driver State: The `exaero` driver allocates persistent Kokkos views once during initialization and reuses them every timestep.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Kokkos Execution and Multi-Rate Dispatch
As an HPC performance engineer, I want the native C++ utility to ingest the block-sparse Kokkos C++ headers generated by the MKPP AOT compiler and execute them using hierarchical parallelism (Kokkos `TeamPolicy`), so that GPU workloads remain perfectly balanced across stiff and non-stiff grid cells.

**Acceptance Scenarios**:
1. **Given** a 3D host domain spanning a dawn/dusk terminator, **When** the utility dispatches the chemistry solve, **Then** grid cells are dynamically sorted by computational intensity (SZA) and assigned to balanced thread teams.
2. **Given** the MKPP headers, **When** the utility invokes the multi-rate solver, **Then** explicit routines step safely alongside the implicit `KokkosBatched` dense micro-matrix steps without causing GPU thread warp divergence.

### User Story 2 - Modular Pre-generated Mechanism Registry
As an atmospheric domain scientist, I want the native driver to support a library of pre-generated, optional mechanism headers alongside the ability to link new configurations dynamically. This ensures that I can switch between standard cycles (e.g., Chapman, CRACMM) at runtime without rewriting the utility.

**Acceptance Scenarios**:
1. **Given** a suite of AOT-compiled MKPP headers, **When** the utility is built, **Then** it compiles them as modular, optionally linkable solver targets.
2. **Given** a host model initialization routine, **When** a specific mechanism name is requested via configuration, **Then** the utility routes execution to the corresponding pre-generated Kokkos kernel without requiring a full recompilation of the host model.

## Requirements *(mandatory)*

### Core Constitution Constraints
- **CON-001**: System MUST strictly adhere to `Kokkos::TeamPolicy` and `Kokkos::TeamThreadRange` to prevent warp divergence.
- **CON-002**: System MUST guarantee zero-copy data interoperability using Fortran-compatible `LayoutLeft` unmanaged views.
- **CON-003**: System MUST fail fast and loudly during module initialization if a requested mechanism is not present in the linked registry.

### Functional Requirements
- **FR-001**: The `exaero` C++ utility MUST ingest MKPP AOT-generated `.hpp` artifacts.
- **FR-002**: The utility MUST implement a workload sorting algorithm to group grid cells by Solar Zenith Angle (SZA) or stiffness before dispatching the Kokkos kernel.
- **FR-003**: The utility MUST implement a Registry pattern that allows multiple distinct chemical mechanisms to be compiled into the library.
- **FR-004**: The utility MUST expose a runtime selection mechanism to choose the active chemistry solver from the Registry.
- **FR-005**: The build system (CMake) MUST provide flags to conditionally compile specific pre-generated mechanisms directly into the main static/shared library.
- **FR-006**: The utility MUST allocate persistent Kokkos views once during initialization for any sorting/scratch buffers, and reuse them at every timestep to avoid dynamic memory allocation overhead.

### Key Entities
- **Mechanism Registry**: The C++ factory/dispatcher that routes state arrays to the correct Kokkos kernel based on runtime configuration.
- **TeamPolicy Dispatcher**: The Kokkos execution manager responsible for launching the hierarchical multi-rate kernel over the SZA-sorted grid.
- **Zero-Copy Host Interface**: The `extern "C"` wrapper that binds Fortran device pointers directly to the selected solver's `Kokkos::MemoryUnmanaged` views.

## Success Criteria *(mandatory)*

### Measurable Outcomes
- **SC-001**: Load Balancing: Nighttime idle starvation is reduced by >= 90% when using the workload sorter compared to linear un-sorted dispatch.
- **SC-002**: Dynamic Switching: The host model successfully swaps between two different compiled mechanisms at runtime without restarting the physical allocation arrays or recompiling.
- **SC-003**: Zero-Copy Overhead: Profiling confirms that moving data from the host model into the utility and down to the hardware execution layer incurs zero memory allocation overhead (0 bytes allocated dynamically during the solver step).

## Assumptions
- Assumes the MKPP AOT Python compiler has successfully generated the `.hpp` files prior to the `exaero` build step.
- Assumes the host model passes a valid configuration string matching a registered mechanism name.
- Assumes the host model is strictly responsible for invoking `Kokkos::initialize()` and `Kokkos::finalize()` outside of the `exaero` driver.

### Edge Cases
- What happens if the host model requests a mechanism name that was not compiled into the registry? (System must fail fast and halt).
- What happens if the grid cells are perfectly homogeneous and don't need sorting? (Sorting algorithm should bypass or evaluate quickly without overhead).
